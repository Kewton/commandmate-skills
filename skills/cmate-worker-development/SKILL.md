# cmate-worker-development

## このスキルが足すのは「方法」であって「権限」ではない

Issue（または `cmate-orchestrate` が渡す実行契約の `goal`）を受け取ったワーカーが、
そこから **commit 済みで、証拠の付いた作業**へ到達するまでの作法を定める。

ワーカーへ渡る文字列は **WHAT（目的・受入条件・境界）と制約**である。
調査せよ・計画を残せ・自分の緑を反証せよ、に相当する指示は**そこに1つも無い**——
**HOW は渡されていない。** その HOW を、リポジトリに依存しない形で埋めるのが本 skill である。

**スラッシュコマンドには依存しない。** スラッシュコマンドはリポジトリスコープであり、
別のリポジトリのワーカーへ送れば `Unknown command` になる。しかも送信自体は成功扱いで返るので、
**呼び出し側から失敗として観測できない**。本 skill が独立 package として存在する理由がそれである。

設計の裁定は
[ADR: ワーカー側の開発スキル](https://github.com/Kewton/commandmate-skills/blob/main/skills/cmate-orchestrate/references/adr-worker-development-skill.md)
に記録されている。ADR は**裁定の記録**であって契約の正本ではない。
食い違ったら、この SKILL.md と `references/` を正本とする。

## 0. 不変条件

**この4つは、本文の他のどの記述にも優先する。**

1. **ゲートを緩めない。** 本 skill はどの検証も置き換えず、どの停止も「制約事項」へ格下げしない。
   裁定は従来どおり実行契約経路の `commandmate wait --verify` の exit code である。
   ワーカーが回す検証は**自己検証**であって裁定ではない。
2. **権限を増やさない。** `scope.allow` を広げない。push / PR 作成 / merge の権限を持たない（第4節）。
3. **契約の外へ出ない。契約と食い違ったら契約が勝つ。** 契約が禁じたことを本 skill が
   許可することはない。本 skill が決めるのは、契約の中で「どう進めるか」だけである。
4. **既定では何も起きない。** install しただけの状態では 1 bit も変わらない。
   呼び出し口は明示 opt-in である。

不変条件 3 が要である。方法論が契約を上書きできる設計にすると、
「契約は PR を作るなと言っているが、方法論は PR を作れと言っている」という
**どちらが勝つか読み手に分からない状態**が生まれる。第4節の裁定はここから出る。
食い違いを見つけたら、契約に従い、**食い違ったこと自体を F 段に記録する**。

> **「適用されたこと」と「守られたこと」は別の事実である。**
> 本 skill を読んで作業したという申告と、実際に走ったコマンドの exit code は、
> どちらも証拠になる。「作法どおりに考えたか」はどこからも測れない。
> **測れないものを測ったふりをしない**（[references/evidence-vocabulary.md](./references/evidence-vocabulary.md)）。

`cmate-orchestrate` との結線——契約の `goal` から本 skill を参照させる経路——は
**この version には無い**。本 skill を install しても、既存の run は何も変わらない。
その結線は別に裁定される（ADR 第12節 段3〜5）。

## 1. いつ使うか

| 状況 | 使えるか |
|---|---|
| 1 Issue を手で開発する（オーケストレーションを使わない） | **使える。** 入力は Issue 本文と、合意した変更範囲 |
| 実行契約（`.commandmate/tasks/<name>.yaml`）を受け取ったワーカー | **使える。** 入力は契約の `goal` と `scope.allow` と完了条件 |
| 契約非対応の経路で prompt だけを受け取ったワーカー | **使える。** ただし境界と完了条件が prompt にしか無いので、A 段で読み落とさないこと |
| PR を出す・merge する・deploy する | **対象外。** 本 skill は commit までで止まる（第4節） |

**挙動を文脈で変えない。** 単独利用かオーケストレーション配下かで、本 skill の手順は変わらない。
「契約 yaml が在れば配下、無ければ単独」という判定は**偽**である——契約非対応 CLI や
契約モードを切った経路では、オーケストレーション配下でも契約 file は存在しない。
最も危険な操作の可否を、構造的に外れる推測で決めない。

## 2. 委譲 — B 段と E 段は再実装しない

B（調査）と E（検証）は、**既存 skill を呼ぶ**。本 skill は手順を持たない。

| 段 | 委譲先 | 呼び出し規約 | 未 install のとき |
|---|---|---|---|
| **B. 調査** | `cmate-repository-analysis` | 入力は同 SKILL.md 第2節の名前だけ——`objective`（必須）/ `roots` / `focus` / `budget`。**引数名を発明しない** | **続行して記録する。** 同 SKILL.md 第1節の6つの問いに、同じ evidence 規律（file/line を付けられない主張は書かない）で自力で答え、**委譲できなかったことを F 段に明記する** |
| **E. 検証** | `cmate-verify` | `verify-run.sh --cwd <worktree> [--gates …]`。判定は exit code（0 `passed` / 2 設定エラー / 20 `failed` / 21 `not_started` / 22 `skipped`）。**`skipped` を `passed` と読まない** | **続行して記録する。** 契約経路なら裁定は `commandmate wait --verify`。それも無ければ契約または profile baseline のコマンドを**実 exit code で**回し、委譲できなかったことを F 段に明記する |

install 先は登録済み worktree の `.claude/skills/<skill-id>/` と `.agents/skills/<skill-id>/` で、
中身は byte-identical である。どちらを読んでも同じものが走る。

**手順を再実装しない。** 走査上限・除外規則・secret 分類は `cmate-repository-analysis` の
`references/` が正本であり、verify.yaml の受理範囲と exit code の意味は `cmate-verify` が正本である。
写せば必ずずれ、ずれたとき読まれるのは写しのほうになる。

**未 install で黙って劣化させない。** 委譲先が無いことは停止理由ではない——
B / E の**問い**は消えず、劣化した形でも答えられるからである。**失われるのは質であって存在ではない。**
だが劣化したことは必ず成果物に書く。黙って質を落とした報告は、
質が落ちていない報告と**見分けがつかない**。

## 3. 手順

### A. 読取 — 契約と Issue を、記憶ではなく現物から読む

契約 file が在るならそれを、無ければ渡された本文と Issue 本文を読み、**5つを書き出す**。

1. **目的** — 何が達成されたら終わりか。
2. **受入条件** — 何をもって受け入れられるか。
3. **境界** — 変更してよい path（`scope.allow` / 「Files you may change」）。
4. **完了条件のコマンド** — 契約が名指ししたゲートとコマンド。**そのまま写す。**
   言い換えない・要約しない・自分の知っている同等コマンドに置き換えない。
5. **明示された禁止事項** — 契約が「するな」と書いたこと。

Issue 番号しか渡されていないなら、本文を**読み取り専用で**取得する（`gh issue view <n>` 等）。
`gh` を PR 作成・merge・close に使わない（第4節）。

読めなかった項目は、**推測で埋めずに止まって訊く**（[references/work-discipline.md](./references/work-discipline.md) 規律 5）。
受入条件と境界のどちらかが読めない状態で着手すると、
**誰も承認していない決定が成果物に入る。**

> ワーカーへ渡る文字列は**生成経路によって文面が違う**。契約経路とフォールバック経路では
> `## Rules` の内容が別物である。読むのは**目の前の契約**であって、
> 前回の run の記憶ではない。

**着手前にベースラインを実測する**（規律 3）。clean な base で完了条件のコマンドを1回回し、
赤が在るならその id と exit code を記録しておく。これをやらないと、
あとで「元から赤だった」を自己申告することになる。

### B. 調査 — `cmate-repository-analysis` へ委譲する

第2節の規約で呼ぶ。`objective` には A 段で書き出した「目的」を渡す。
`focus` には契約の `suspected_files` から導いた語を渡す。

得たいのは、そのリポジトリの**流儀**（`AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING.md` /
README / CI 定義）と、目的に関係する**既存実装**と、**壊れうる箇所**である。
リポジトリ固有の作法は**そのリポジトリの文書が正本**であって、本 skill ではない。
本 skill の規律とリポジトリの作法が食い違ったら、リポジトリの作法を採る
（契約が言及しているなら、契約が勝つ）。

**Issue 本文の前提を、ここでコードに突き合わせる**（規律 4）。行番号・関数名・
「〜は存在しない」という主張は、Issue が書かれた時点の実測であって現在の実測ではない。
**食い違ったら実測を正とする。** 自分が行番号を書くときは、どの commit の実測かを添える。

### C. 計画 — 変更集合と、それを判定するものを先に決める

書くのは3つ。長い文書は要らない。**後で証拠に転記できる形**であればよい。

1. **変更集合** — どの file を、なぜ、どう変えるか。
   **`scope.allow` の内側に収まることを、ここで確かめる**（規律 6）。
   収まらないなら、広げるのではなく止まって訊く。
2. **受入条件 → 検証手段の対応表** — 受入条件それぞれについて、どのゲートが担保するかを
   対応付ける。どのゲートにも担保されない条件は**消さず「ゲート外」として列挙**し、
   UAT / 人間の確認へ残す。担保されない条件を黙って落とすことが、すり抜けの正体である。
3. **二点測定の計画** — この変更を判定するのは何か。それをどう変異させれば赤になるか。
   **test-first を推奨する**——実装が無い時点なら赤が無料で手に入る。
   ただし強制はしない。後からテストを書いて実装を戻し、赤を観測するのも同じ測定である
   （規律 1）。文書のみの変更で成立しないときの扱いも同じ規律に書いてある。

### D. 実装 — 境界の内側で、最小の変更を作る

- **`scope.allow` の外に触らない**（規律 6）。触りたくなったら止まって訊く。
- **既存テストの期待値を、実装を通すために書き換えない**（規律 2）。
  落ちたら、まず自分の実装を疑う。
- **生成物は再生成コマンドで作る**（規律 7）。digest・manifest・生成コードを手で書かない。
- **破壊的・曖昧・ブロックのときは止まって訊く**（規律 5）。
- 契約が commit の作り方を定めているなら、それに従う。定めが無ければ**単一 commit** にする。
  commit されていない作業は、検証を通っていても下流へ流れない。

### E. 検証 — `cmate-verify` へ委譲する

第2節の規約で呼ぶ。判定は**実 exit code** で読む。

**出力の grep で合否を決めない。** `cmd | grep …` はパイプ先の終了状態を返すので、
非ゼロ終了を隠す。全テスト緑でも exit 1 を出しうる runner が在り、
出力を要約した判定は**それを PASS と報告する**。

そのうえで **二点測定**を実行する（規律 1）。

1. 適合状態で緑を実測する。
2. **成果物側**に変異を入れて赤を実測する。ゲートやランナーを壊す変異ではない——
   それは harness が動くことの証明であって、ゲートが当の変更を測っている証明ではない。
3. 赤の理由を固定する。証拠になる赤は exit 20 で、**失敗ゲートに当の id が名指しで**含まれるもの
   だけである。exit 2 / 21 / 22 / 127 の赤は**判定に到達していない**。
4. 復元して緑に戻ることを実測する。

**どちらの機構で測ったかを必ず記録する。** 裁定機構は2つ在りうる——実行契約経路の
`commandmate wait --verify` と、`cmate-verify` の `verify-run.sh` である。
**ワーカーが回すのは自己検証であって裁定ではない**（不変条件 1）。裁定は呼び出し側が取る。

### F. 証拠 — 転記であって主張ではない

節構成と語彙の正本は [references/evidence-vocabulary.md](./references/evidence-vocabulary.md) である。
**新語彙を作らない**——そこに並ぶ語はすべて、`cmate-orchestrate` が PR 本文で確立した
節構成と由来語彙のミラーであり、レビュー時に突き合わせるためにミラーにしてある。

書くのは、Summary / Verification（どの機構で測ったか・Gates 表・Checks 表）/
二点測定 / 宣言 scope と実変更 / 受入条件との対応（ゲート外を含む）/
読めなかったこと・委譲できなかったこと、である。**節を削らない。**
該当が無い節は「該当なし」とその理由を書く——空の節と、無いことを確かめた節は別の事実である。

規律は3つ。**証拠は転記であって主張ではない**（「検証した」ではなく、何がどの exit code で
終わったかを写す）。**打ち切ったら打ち切ったと書く**（何件載せていないかを書く）。
**緑の意味を広げない**（`passed` は「宣言したゲートが通った」以上を意味しない）。

主成果物は**人が読む markdown** である。機械可読 JSON の schema は定義しない——
今この文書を機械で読む consumer が存在しないからである。理由は同 reference に書いてある。

## 4. PR は作らない。push もしない

**本 skill は PR を作らない。push もしない。merge もしない。**
単独利用でもオーケストレーション配下でも、この挙動は変わらない。理由は5つ。

1. **オーケストレーション配下では二重になる。** merge runner は、検証を通った Issue **だけ**を
   PR にする。ワーカーが先に作ると「検証を通っていないものが PR になっている」状態が生まれ、
   merge の 2 gate（承認 + CI）の前提が崩れる。
2. **push と PR 作成は外部に出る操作である。** 取り消せるのはリポジトリの状態であって、
   送られた通知ではない。確信の持てない破壊をしないことの裏返しとして、
   **確信の持てない外部発信もしない**。
3. **文脈判定は構造的に外れる**（第1節）。最も危険な操作の可否を、外れる推測で決めない。
4. **契約と整合する。** 実行契約の Rules は「単一 commit を作れ。それが作業の終わりである」と
   書いており、PR には言及していない。本 skill が PR を作れば、契約と本 skill が別のことを言う
   （不変条件 3 に反する）。
5. **手書きで回避されてきた。** 実運用では契約に「PR を作らない・push しない」を
   毎回**手書き**して二重 PR を避けていた。**その手書きが不要になることが、本 skill の効果の1つである。**

**「作らない」は「出せない」ではない。** PR に必要な素材は F 段が残す。
単独利用者は人間がそれを貼って PR を作る。オーケストレーション配下では、
merge runner が自分の測定で PR 本文を作り、ワーカーの証拠は**突き合わせ材料**になる。

## 5. 完了条件

次の**すべて**を満たしたときにだけ、完了と報告する。
**報告の文面は完了条件ではない**（規律 8）。

1. 契約（または合意した）完了条件のコマンドが、**実 exit code で**緑である。
   `skipped`（exit 22）と `not_started`（exit 21）は緑ではない。
2. 二点測定が済んでいる——または、成立しない変更であることを機械で示せる範囲で示し、
   代わりに「主張 → 実測」の対応表を置いている（規律 1）。
3. 変更が `scope.allow` の内側に収まっている。out-of-scope が 0 件であることを実測した。
4. 契約が定める形で commit されている（定めが無ければ単一 commit）。
5. F 段の証拠が在り、ゲート外の受入条件と、読めなかった・委譲できなかったことが書かれている。
6. **push / PR 作成 / merge を1つも行っていない。**

満たせないものが在るなら、**満たしたふりをせず、満たせないものを名指しして止まる。**
止まったことは失敗ではない。推測で進んだことが失敗である。
